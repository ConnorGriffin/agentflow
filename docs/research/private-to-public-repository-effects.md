# GitHub issue #136: effects of making the existing private repository public

**Research date:** 2026-07-16

**Issue:** [#136 — Determine the effects of making the existing GitHub repository public](https://github.com/ConnorGriffin/agentflow/issues/136)

**Question:** What changes when an existing repository on GitHub.com is made public in place?

**Evidence policy:** GitHub documentation and other GitHub first-party sources only. No GitHub state was changed, and no secret value is reproduced or reported.

## Evidence labels

- **Documented fact** — GitHub states the behavior directly.
- **Repository observation** — verified in this checkout without changing it or disclosing a secret value.
- **Inference** — the behavior follows from GitHub's resource/API model, but GitHub does not publish a complete visibility-change contract for that resource.
- **Recommendation** — a go/no-go or risk-reduction action based on the documented behavior.
- **Uncertainty — VERIFY IMMEDIATELY** — GitHub's first-party material does not settle the behavior; check the real repository in the UI/API immediately before or after the change.

## Executive conclusion

Changing visibility in place is operationally simple but not a reversible confidentiality switch. GitHub explicitly says the repository code, historical Actions logs, and activity become public; all push rulesets are disabled; stars and watchers are erased; private forks are detached; and even commits previously pushed only to those private forks are migrated into a new public repository network and become visible to everyone. Anyone can then fork the repository. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility), [GitHub: what happens to forks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/what-happens-to-forks-when-a-repository-is-deleted-or-changes-visibility)

GitHub does **not** publish an exhaustive statement that every attached object and setting is preserved. The most defensible model is that the same repository object is updated in place, so issues, pull requests, releases, settings, credentials, hooks, and IDs should remain unless GitHub documents a visibility-specific exception. That is an **inference**, not a migration guarantee: record non-secret metadata before the change and compare it immediately afterward. GitHub's REST API models the operation as `PATCH /repos/{owner}/{repo}` with `visibility: public`, while the owner and repository name remain path parameters. [GitHub REST: update a repository](https://docs.github.com/en/rest/repos/repos#update-a-repository)

**Recommendation:** treat publication as permanent disclosure. Do not proceed until repository history, private-fork history, collaboration content, Actions history/artifacts/caches, release assets, Pages, packages, non-secret variables, deployments, integrations, and credentials have been audited. If a credential may have appeared anywhere, revoke or rotate it before publication; GitHub says rotation/revocation is the first step even when history will later be rewritten. [GitHub: removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

## Immediate go/no-go checks

These are the items whose exact state must be verified in the GitHub UI or API. Inventory names, IDs, policies, counts, and timestamps only; do not retrieve or record secret values.

1. **VERIFY IMMEDIATELY — authority and policy.** Confirm the actor is allowed to change visibility and that organization/enterprise policy permits public visibility. Admin access is normally required, but an organization can reserve visibility changes to owners. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility), [GitHub: restricting repository visibility changes](https://docs.github.com/en/organizations/managing-organization-settings/restricting-repository-visibility-changes-in-your-organization)
2. **VERIFY IMMEDIATELY — private fork network.** Enumerate every private fork and every branch/commit not present in the root repository. GitHub says all commits previously pushed to private forks become visible in the new public network even though the forks themselves detach and remain private. [GitHub: what happens to forks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/what-happens-to-forks-when-a-repository-is-deleted-or-changes-visibility)

Secret scanning for public repositories also scans historical issues, pull requests, discussions, and wikis for partner patterns, so collaboration text is part of the exposure surface. Deleting a workflow run permanently deletes its associated artifacts; artifacts may also be removed individually. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility), [GitHub: managing rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository)

## Surface-by-surface effects

### Repository contents, issues, and discussions

- **Documented fact:** A public repository is accessible to everyone on the internet, and GitHub specifically says the code becomes visible to everyone who can visit GitHub.com. GitHub also says the visibility change is published as activity. [GitHub: about repositories](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories), [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)
- **Documented fact:** Public issue resources can be read through the REST API without authentication. Once the repository is public, issue bodies, comments, labels, milestones, assignees, and ordinary timeline content should be treated as public repository content. [GitHub REST: issues](https://docs.github.com/en/rest/issues/issues)
- **Documented fact:** A discussion inherits the visibility of the repository where it was created. [GitHub: Discussions quickstart](https://docs.github.com/en/discussions/quickstart)
- **Documented fact:** Organization issue fields can remain `Organization only` even on a public repository; public field visibility is a separate setting, and new/existing issue fields default to organization-only. [GitHub: managing issue fields](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/managing-issue-fields-in-your-organization)
- **Documented fact:** Anyone with read access can view a comment's edit history. A comment author or repository writer can delete sensitive revision content, but the editor identity and edit time remain visible. Audit historical revisions as well as current issue, PR, and discussion text; editing the visible comment alone is insufficient. [GitHub: tracking changes in a comment](https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment)
- **Inference:** Existing issues, comments, labels, milestones, discussions, categories, reactions, and numbers remain attached to the same repository and become readable according to the new public access boundary. GitHub documents no deletion or renumbering step for these resources, but it does not state preservation explicitly. [GitHub REST: update a repository](https://docs.github.com/en/rest/repos/repos#update-a-repository), [GitHub: Discussions visibility](https://docs.github.com/en/discussions/quickstart)
- **Recommendation:** Review titles, bodies, comments, attachments, cross-links, email addresses, customer/internal names, incident details, and issue/discussion templates before publication. GitHub's public partner scanning includes open and closed historical issue content, PR content, discussions, and wikis. [GitHub: secret scanning for partners](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning-for-partners)
- **Uncertainty — VERIFY IMMEDIATELY:** Confirm that issue/discussion enablement, creation policy, moderation permissions, organization-only issue fields, pinned discussions, and every old URL behave as intended. GitHub does not document whether a visibility change modifies these independent settings. [GitHub REST: repository settings](https://docs.github.com/en/rest/repos/repos#update-a-repository), [GitHub: issue-field visibility](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/managing-issue-fields-in-your-organization)

### Collaborators, teams, and access

- **Documented fact:** Public visibility gives everyone read access; it does not grant anonymous users write, maintain, or admin permission. Repository roles remain the control for privileged actions. [GitHub: repository roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)
- **Inference:** Existing collaborators, teams, custom roles, pending invitations, and their write/maintain/admin access remain attached to the in-place repository. GitHub's visibility documentation names fork, Actions, ruleset, activity, star/watcher, and security consequences but does not say privileged access assignments are deleted. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility), [GitHub: teams and people](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-teams-and-people-with-access-to-your-repository)
- **Uncertainty — VERIFY IMMEDIATELY:** Export and compare direct collaborators, teams, outside-collaborator classification, custom roles, pending invitations, security-manager access, ruleset bypass actors, and base permissions. Remove access only as a separate reviewed decision.

### Pull requests and reviews

- **Documented fact:** Anyone with read access can review and comment on a pull request. By default on a public repository, any user can submit an approval or request changes; administrators can limit approving/request-changes reviews to users with explicit read access or higher. [GitHub: about pull-request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews), [GitHub: managing pull-request reviews](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-pull-request-reviews-in-your-repository)
- **Documented fact:** Public and private repositories can independently disable pull requests or restrict new PR creation to collaborators; when PRs are disabled, existing PRs are not visible through the repository UI. [GitHub changelog: pull-request access settings](https://github.blog/changelog/2026-02-13-new-repository-settings-for-configuring-pull-request-access/), [GitHub REST: update a repository](https://docs.github.com/en/rest/repos/repos#update-a-repository)
- **Inference:** Existing PR numbers, bodies, comments, reviews, review threads, checks, base branches, and URLs remain. Their contents become public because they belong to a now-public repository. [GitHub REST: update a repository](https://docs.github.com/en/rest/repos/repos#update-a-repository), [GitHub: about pull-request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)
- **Uncertainty — VERIFY IMMEDIATELY:** GitHub does not document what happens to an open PR whose head branch belongs to a private fork that is detached during publication. Confirm head references, diffs, mergeability, pending review requests, approvals, auto-merge, merge queue entries, and status checks for every open PR before relying on it. [GitHub: what happens to forks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/what-happens-to-forks-when-a-repository-is-deleted-or-changes-visibility)
- **Recommendation:** Explicitly set the public PR creation and review policy instead of accepting a default. Re-check branch/ruleset requirements that decide whether outside approvals count. [GitHub: managing pull-request reviews](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-pull-request-reviews-in-your-repository), [GitHub: protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule)

### GitHub Actions: runs, logs, artifacts, and caches

- **Documented fact:** All existing Actions history and logs become visible to everyone. Logs can also reveal the repository/path of reusable or required workflows shared from another repository in the organization. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)
- **Documented fact:** A signed-in GitHub user with read access can download unexpired workflow artifacts. Because everyone has read access to a public repository, existing artifacts become downloadable to signed-in users unless deleted or expired. Default log/artifact retention is 90 days, subject to configuration. [GitHub: downloading workflow artifacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)
- **Documented fact:** Public repositories can configure cache retention only up to 90 days versus 365 days for private/internal repositories. Public artifact/log retention can be 1–90 days versus 1–400 days for private repositories, and a changed artifact/log retention setting applies only to newly created objects. [GitHub: Actions repository settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)
- **Documented fact:** Deleting a workflow run permanently deletes its associated artifacts; artifacts can also be deleted individually. [GitHub: deleting a workflow run](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/delete-a-workflow-run), [GitHub: removing workflow artifacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts)
- **Documented fact:** Cache entries are branch-scoped, but a pull request from a fork can restore caches from the base branch. GitHub explicitly warns not to cache sensitive information because anyone able to open a PR can access base-branch cache contents. [GitHub: dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)
- **Documented fact:** Public-fork workflows do not receive repository secrets, and first-time contributors require workflow approval by default. `pull_request_target` runs in the trusted base context regardless of that approval setting; GitHub warns that privileged triggers combined with untrusted checkout can compromise the repository. [GitHub: Actions repository settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), [GitHub: secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)
- **Inference:** Workflow/run/artifact IDs, URLs, retention settings, and ordinary repository Actions configuration remain. GitHub documents visibility of history, not deletion or ID replacement. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility), [GitHub REST: workflow runs](https://docs.github.com/en/rest/actions/workflow-runs)
- **Uncertainty — VERIFY IMMEDIATELY:** Private-repository fork options—sending write tokens, sending secrets, and private-fork approval—are private-only settings. GitHub does not state exactly how they are translated when the repository becomes public. Verify the effective public-fork approval policy, `GITHUB_TOKEN` default, self-hosted runner groups, and secret delivery with a harmless test. [GitHub: Actions repository settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)
- **Uncertainty — VERIFY IMMEDIATELY:** GitHub documents the lower public-repository retention ceilings but not how a private setting already above those ceilings is normalized during conversion. Record the configured values and each retained object's own expiry before publication; compare immediately afterward. [GitHub: Actions repository settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)
- **Recommendation:** Review every historical run/log/artifact and delete unsafe material before publication. Purge caches rather than assuming they are harmless or inaccessible. Audit `pull_request_target`, `workflow_run`, issue-comment dispatch, self-hosted runners, write-capable tokens, and reusable workflows before accepting public contributions. GitHub says automatic redaction is not guaranteed. [GitHub: secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)

### Variables, secrets, and environments

- **Documented fact:** GitHub variables are for non-sensitive configuration and render unmasked in build output by default. Repository/environment variable values are not made anonymously readable by the variables API—it requires collaborator access—but a workflow can print them into logs that are now public. [GitHub: variables](https://docs.github.com/en/actions/concepts/workflows-and-actions/variables), [GitHub REST: Actions variables](https://docs.github.com/en/rest/actions/variables)
- **Documented fact:** GitHub stores secret values encrypted; secret-listing APIs return metadata without revealing encrypted values. [GitHub: secret types](https://docs.github.com/en/code-security/reference/secret-security/secret-types), [GitHub REST: Actions secrets](https://docs.github.com/en/rest/actions/secrets)
- **Documented fact:** Organization-level Actions variables/secrets, Dependabot secrets, and Codespaces secrets support repository-access policies `all`, `private`, or `selected`. A repository that becomes public no longer matches a `private`-repositories policy; `selected` is repository-ID based. [GitHub REST: Actions secrets](https://docs.github.com/en/rest/actions/secrets), [GitHub REST: Actions variables](https://docs.github.com/en/rest/actions/variables), [GitHub REST: Dependabot secrets](https://docs.github.com/en/rest/dependabot/secrets), [GitHub REST: Codespaces organization secrets](https://docs.github.com/en/rest/codespaces/organization-secrets)
- **Documented fact:** Environments, environment secrets, deployment branches, and deployment protection rules are available to public repositories on all current plans. Several protections that require a paid plan for private repositories are available on public repositories on Free/Pro/Team. ### Forks, stars, and watchers

- **Documented fact:** Existing private forks remain private but are disconnected from the repository. Each becomes a standalone private repository with its own independent network. Future changes in those networks are not accessible from the now-public root. [GitHub: what happens to forks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/what-happens-to-forks-when-a-repository-is-deleted-or-changes-visibility)
- **Documented fact:** Despite that detachment, all commits previously pushed to those private forks are migrated into a new public repository network and become visible to everyone. This is the highest-risk non-obvious consequence. [GitHub: what happens to forks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/what-happens-to-forks-when-a-repository-is-deleted-or-changes-visibility)
- **Documented fact:** Anyone can fork the public repository. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)
- **Documented fact:** Existing stars and watchers are erased on the private-to-public change. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)
- **Inference:** GitHub documents no restore path for stars/watchers erased by this change; assume users must star/watch again. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)
- **Uncertainty — VERIFY IMMEDIATELY:** Record the private fork inventory and star/watcher/subscriber counts before the change, then confirm the resulting fork networks and counts. [GitHub: what happens to forks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/what-happens-to-forks-when-a-repository-is-deleted-or-changes-visibility)

## Reversibility

- **Documented fact:** The repository can later be made private again, subject to permissions and plan. That reverse operation detaches public forks rather than making them private, erases stars/watchers again, can unpublish Pages on Free, and can disable Advanced Security features without a private-repository license. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)
- **Documented fact:** Public forks created while the repository is public remain public in a detached network if the root is later made private. Previously detached private forks also remain independent. [GitHub: what happens to forks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/what-happens-to-forks-when-a-repository-is-deleted-or-changes-visibility)
- **Inference:** Anyone can clone, archive, index, or copy data while the repository is public; making it private later cannot recall those copies. GitHub's sensitive-data-removal guidance explicitly warns that existing clones and forks retain removed data and require coordination. [GitHub: removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)
- **Documented fact:** Public repositories are included in the GitHub Archive Program by default. An administrator can opt a public repository out, but that controls future Archive Program processing; it does not recall copies already made by ordinary users, forks, caches, or prior archives. **DIFFICULT TO REVERSE:** decide the Archive Program policy before publication and apply it as soon as the setting is available. [GitHub: opting in or out of the Archive Program](https://docs.github.com/en/get-started/archiving-your-github-personal-account-and-public-repositories/opting-into-or-out-of-the-github-archive-program-for-your-public-repository), [GitHub: archiving public repositories](https://docs.github.com/en/repositories/archiving-a-github-repository/about-archiving-content-and-data-on-github)
- **Documented fact:** Stars/watchers are not recoverable, Pages URLs change across visibility transitions, and a granular package deliberately made public cannot later be made private. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility), [GitHub: Pages 404 troubleshooting](https://docs.github.com/en/pages/getting-started-with-github-pages/troubleshooting-404-errors-for-github-pages-sites), [GitHub: package access and visibility](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility)
- **Uncertainty — VERIFY IMMEDIATELY:** GitHub says push rulesets are disabled, not how/when they can be restored after another visibility change. Record them before publication and verify manually on every transition. [GitHub: setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility), [GitHub: managing rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository)

**Conclusion:** The visibility field is reversible; the disclosure and network effects are not. A later return to private does not reconstruct the original private repository state.
